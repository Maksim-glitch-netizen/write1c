# Проверенные рабочие сценарии

Это справочные сценарии синтаксиса. Применение определяют `AGENTS.md`, профиль и разрешения
текущего проекта. Источник актуальных исходников основной конфигурации и каждого расширения
выбирается отдельно: `working_configuration` либо `repository`. Хранилище предлагай отдельным
вопросом с вариантами только при подтверждённом наличии соответствующего хранилища; без него
используй рабочую конфигурацию. Конфигурацию БД источником не предлагай.
При `working_configuration` выгружай свежие XML Конфигуратора без получения из хранилища ради
baseline. При `repository` и разрешённой синхронизации сначала получи актуальную версию,
проверь результат, затем выгрузи получившуюся рабочую конфигурацию через `DumpConfigToFiles`.
Сценарии 1 и 2 требуют разрешения на получение; обновление БД также должно быть отдельно
требуемым и разрешённым. При запрете или ошибке требуемой синхронизации останови этап.
Недостающие параметры уточняй строго по одному вопросу за раз, по возможности с вариантами.

## 1. Получить основную конфигурацию и обновить базу

Открой: `01-common-cli.md`, `04-repository-read-bind.md`, `06-update-db-cfg.md`, `08-results-errors.md`.

```text
/ConfigurationRepositoryF "<путь-хранилища>"
/ConfigurationRepositoryN "<пользователь>"
/ConfigurationRepositoryP "<пароль>"
/ConfigurationRepositoryUpdateCfg -force
/UpdateDBCfg -Dynamic+
```

Пароль хранилища не указывай, если он не требуется. `/UpdateDBCfg` документирован как допустимая следующая команда после `ConfigurationRepositoryUpdateCfg`.

## 2. Получить расширение и обновить его базовую конфигурацию

```text
/ConfigurationRepositoryF "<путь-хранилища-расширения>"
/ConfigurationRepositoryN "<пользователь>"
/ConfigurationRepositoryP "<пароль>"
/ConfigurationRepositoryUpdateCfg -force -Extension "<имя>"
/UpdateDBCfg -Dynamic+ -Extension "<имя>"
```

`-Extension` указывается отдельно у каждой операции.

## 3. Первая и последующая XML-выгрузка

Первая:

```text
/DumpConfigToFiles "<каталог>" -Format Hierarchical
```

Последующая при подтвержденном `ConfigDumpInfo.xml`:

```text
/DumpConfigToFiles "<тот-же-каталог>" -update
```

Для расширения добавь его точное имя через `-Extension`. Самостоятельное сравнение без
обновления XML выполняют отдельно:

```text
/DumpConfigToFiles "<тот-же-каталог>" -update -getChanges "<файл-изменений>"
```

`-getChanges` создаёт только список отличий и не подтверждает актуализацию XML или контрольную
выгрузку после изменения. Для такой выгрузки выполняй команду без `-getChanges` и проверь файлы.

## 4. Загрузить известные XML-файлы и обновить базу

```text
/LoadConfigFromFiles "<каталог-xml>" -listFile "<utf8-файл-списка-путей>" -Format Hierarchical
/UpdateDBCfg -Dynamic+
```

Добавляй `-partial` только при загрузке отдельной части объекта.

## 5. Изменение объектов расширения, подключенного к хранилищу

1. Проверь выбранный источник, права и текущую привязку расширения к его собственному хранилищу.
   При `repository` и разрешённой синхронизации получи актуальную версию через
   `ConfigurationRepositoryUpdateCfg -Extension` и проверь результат. При
   `working_configuration` не получай из хранилища ради baseline. При запрете или ошибке
   синхронизации, требуемой выбранным источником, останови этап.
2. Выгрузи свежие XML рабочей конфигурации расширения через `DumpConfigToFiles -Extension`.
3. Проанализируй свежие XML и зафиксируй изменяемые объекты.
4. Захвати объекты: `ConfigurationRepositoryLock -Objects ... -Extension`.
5. Измени запланированные файлы, затем частично загрузи XML:
   `LoadConfigFromFiles -files/-listFile -Format ... -Extension`.
6. Проверь расширение допустимыми по `AGENTS.md` средствами.
7. Если требуется и разрешено, обнови базу: `UpdateDBCfg -Extension`.
8. Повторно выгрузи рабочую конфигурацию расширения без `-getChanges`, проверь изменения
   и выполни функциональное тестирование.
9. При наличии разрешения помести объекты:
   `ConfigurationRepositoryCommit -Objects ... -comment ... -Extension`.

Файл `-Objects` и список XML-файлов являются разными форматами.

## 6. Зарегистрировать новый корневой объект через donor.cf

Открой: `01-common-cli.md`, `02-xml-dump.md`, `03-xml-load.md`, `08-results-errors.md` и
`11-merge-cfg.md`.

1. Подтвердить отсутствие явно заданного `<Тип>.<Имя>` в свежем baseline основной конфигурации.
2. Создать отдельную файловую ИБ с минимальной donor-конфигурацией и только самодостаточным каркасом
   нового объекта.
3. Полностью загрузить donor XML в рабочую конфигурацию файловой ИБ; `UpdateDBCfg` не выполнять.
4. Выгрузить рабочую donor-конфигурацию через `DumpCfg`.
5. Сформировать настройки: `Configuration=DoNotMerge`, целевой объект=
   `GetFromSecondConfiguration`, все остальные объекты donor=`DoNotMerge`.
6. Выполнить один `MergeCfg` в основной конфигурации без опасных параметров по умолчанию.
7. Сразу повторно выгрузить XML основной рабочей конфигурации и подтвердить единственное добавление.
8. Продолжить разработку уже зарегистрированного объекта обычной частичной XML-загрузкой.

Не обновлять конфигурацию БД между регистрацией каркаса и его контрольной XML-выгрузкой.

## Правило остановки

При ненулевом результате, отсутствующем `/DumpResult`, ошибке в `/Out` или отсутствии ожидаемого фактического результата не переходи к следующему шагу.
