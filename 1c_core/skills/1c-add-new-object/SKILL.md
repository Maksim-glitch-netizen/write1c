# Добавление нового объекта через donor.cf

Объект задается явно парой `Тип + Имя`. Не определяй его по Git diff или сравнению двух
`Configuration.xml`. Сравнение состава применяется только как проверка отсутствия до merge и
единственности добавления после merge.

Источник актуальных исходников определяет AGENTS проекта: рабочая конфигурация
Конфигуратора либо подтверждённое хранилище. При выбранном хранилище сначала выполняется
разрешённое получение, затем свежая выгрузка рабочей конфигурации. Конфигурацию БД
вместо выбранного источника не используй. Недостающие входы выясняй строго по одному
вопросу за раз, с вариантами ответа, где это возможно, и ожиданием предыдущего ответа.

## Обязательные зависимости

До начала проверь доступность:

- `cf-init` - создать XML пустой donor-конфигурации;
- `meta-compile` - создать минимальный объект и зарегистрировать его в donor `Configuration.xml`;
- `meta-validate` и `cf-validate` - проверить XML donor;
- `db-create` - создать отдельную файловую ИБ donor;
- `1c-configurator-batch-8-3-27` - сформировать и выполнить `LoadConfigFromFiles`, `DumpCfg`,
  `MergeCfg` и контрольную XML-выгрузку.

Если обязательная зависимость недоступна, останови текущий этап. Не заменяй ее ручным XML по
догадке.

## Границы

Скилл предназначен для нового корневого объекта основной конфигурации. Он не переносит:

- новую форму, команду или макет существующего объекта;
- изменения существующих объектов;
- объект расширения;
- бизнес-данные.

Для объекта с обязательной ссылкой на другие метаданные сначала прочитай
[ограничения donor](references/workflow.md#обязательные-ссылки). Если самодостаточный минимальный
объект создать нельзя, не применяй упрощенный donor.

## Рабочий процесс

1. Получи свежую XML-выгрузку рабочей конфигурации Конфигуратора основной конфигурации DEV
   по выбранному источнику и правилам проекта.
2. Зафиксируй точные `Тип`, `Имя` и полное имя `<Тип>.<Имя>` в `task.md`.
3. Запусти `scripts/new_object_workflow.py prepare`. Скрипт проверит имя, тип и отсутствие объекта
   в свежем `Configuration.xml`, сохранит неизменяемый снимок baseline, затем создаст рабочую
   структуру и `input/object.json`.
4. Создай donor XML через `cf-init`, затем добавь содержимое `input/object.json` в donor XML через
   `meta-compile`. Для регистра накопления генератор автоматически добавляет donor-only документ-
   регистратор и два технических поля каркаса, потому что платформа не загружает регистр без
   регистратора и без данных. В основную конфигурацию документ не переносится; технические поля
   необходимо удалить или заменить при дальнейшей разработке.
5. Выполни `meta-validate` и `cf-validate` для donor XML.
6. Запусти `scripts/new_object_workflow.py finalize`. Скрипт проверит состав donor и создаст
   `MergeSettings.xml`: корень и все вспомогательные объекты получают `DoNotMerge`, целевой объект -
   `GetFromSecondConfiguration`.
7. Создай новую файловую ИБ donor. Не добавляй ее в список баз пользователя.
8. Полностью загрузи donor XML в рабочую конфигурацию файловой ИБ. Не выполняй `UpdateDBCfg`.
9. Выгрузи рабочую конфигурацию файловой ИБ в `donor.cf` командой `DumpCfg`.
10. Проверь журналы, `/DumpResult`, наличие непустого `donor.cf` и структуру `MergeSettings.xml`.
11. Выполни один `MergeCfg` в DEV. По умолчанию не используй `-force`,
    `-ClearUnresolvedRefs` или `-IncludeObjectsByUnresolvedRefs`.
12. Не выполняй `UpdateDBCfg` для каркаса. Сразу повторно выгрузи XML из рабочей конфигурации DEV.
13. Запусти `scripts/new_object_workflow.py verify-main`. Продолжай только если добавлен ровно
    целевой объект, ничего не удалено и файл объекта присутствует.
14. Дальше изменяй уже выгруженный объект обычными skills. После разработки запусти
    `verify-ready`: все элементы из manifest `bootstrapMembersToReplace` должны быть удалены или
    осознанно переименованы; регистр накопления должен получить реальный документ-регистратор.
15. Выполни `meta-validate`, `cf-validate` и только затем финальный `UpdateDBCfg`.

Подробные команды, структура каталогов и правила остановки находятся в
[workflow.md](references/workflow.md). Формат входов скрипта описан в
[tooling.md](references/tooling.md).

После изменения skill запусти `scripts/validate-skill.ps1`; он проверяет структуру и выполняет
unit tests генератора и проверок.

## Строгие правила остановки

- Объект уже есть в свежей основной конфигурации - не создавать donor, перейти к редактированию.
- Donor содержит другой объект с правилом, отличным от `DoNotMerge` - не выполнять merge.
- Есть неразрешенная ссылка - не очищать и не подключать объект автоматически, остановиться.
- `MergeCfg` завершился с ошибкой, предупреждением, неопределенным результатом или диалогом - не
  выполнять повтор автоматически и не продолжать разработку.
- Контрольная выгрузка не подтверждает единственное добавление - не выполнять `UpdateDBCfg`.
