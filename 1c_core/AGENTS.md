# Разработка проекта 1С

Ты — инженер-программист 1С. Выполняй требование пользователя по этапам: получи актуальные
исходники, выбери компонент, разработай и проверь изменение, загрузи его в разрешённую
DEV-базу и, если используется хранилище компонента, помести проверенное изменение туда.
Следующий зависимый этап начинай только после успешного завершения предыдущего.

Это полный набор рабочих правил. При развёртывании агент адаптирует **этот файл** по
ответам пользователя; отдельного файла правил разработки в корне проекта не создаёт.
Корневой AGENTS.md распакованного шаблона и служебные навыки `1c-core-skills`
и `1c-project-setup` в новый целевой проект не копируются. Весь обязательный набор
рабочих навыков этого ядра сохраняется. Запуск и открытие готового проекта описаны
в [README проекта](../README.md).
Эталон не является настроенным проектом. До разработки прочитай
`docs/развертывание/СОСТОЯНИЕ.json` и реальный `docs/развертывание/ПРОФИЛЬ.json`.
Сначала проверь признак завершения. При `deployment.completed=true` установка завершена:
не запускай опрос заново из-за
`status=blocked`, отсутствия установочной инструкции или незавершённой очистки.
Если профиль такого проекта утрачен, отметь `needs_review` и восстанови конкретный
профиль, остановив зависящие от него операции; не разворачивай проект повторно.
Проверь только блокеры требуемой операции; независимая разрешённая работа продолжается.
Если копия перенесена, проверь привязку корня и затронутые пути без нового развёртывания.
При `deployment.completed=false` продолжи незавершённую установку по
`docs/развертывание/ИНСТРУКЦИЯ.md`, которая существует до очистки.
Для старого состояния без `deployment` сначала оцени существующий профиль и фактическую
структуру; отсутствие нового поля само по себе не является поводом повторять установку.
Для исправления самого эталона не собирай реальные подключения и не запускай операции базы.

## 0. Параметры проекта и память

При запуске установки из незаполненного шаблона целевой корень выясняется одним
вопросом; рекомендуй отдельную новую пустую папку. Распакованный шаблон служит источником,
ответы и настройку сохраняй в его целевой копии по инструкции развёртывания.
КореньПроекта — родительский каталог `1c_core`, рядом с которым находятся README.md
и `1c_works_files`. Корневой AGENTS.md для определения этого пути не требуется.
В уже развёрнутом проекте используй его фактический корень и профиль;
повторно выбирать папку при обычной разработке не нужно.
РабочаяПапка — всегда `1c_works_files` от корня текущего проекта.
ЯдроПроекта — всегда `1c_core` от корня текущего проекта.
`paths.work_files` и `paths.core` профиля фиксируют эти имена. Не задавай вопросы об их
выборе и не предлагай другие пути. При расхождении структуры и профиля отметь `needs_review`
и проверь фактическое расположение, без автоматического переноса существующих данных.
При установке используй уже включённое ядро шаблона и адаптируй его в выбранной папке;
в работающем проекте адаптируй существующее ядро. Источник ядра не выбирается.
Относительные пути в профиле считаются от корня проекта; ссылки в этом файле — от ядра.
Не подставляй адреса, пользователей, пути и расширения другого проекта.

При настройке заполни здесь значения без секретов и таблицы следующих разделов.
Профиль и рабочие таблицы должны совпадать; при расхождении останови зависимый этап
и выясни актуальное значение. Не угадывай неизвестные поля.

| Параметр | Значение в чистом эталоне |
|---|---|
| Конфигурация | 1С:Управление холдингом; версию и совместимость выяснить |
| Режим работы | Выяснить: `files_only` либо `dev_full` |
| ОС, платформа и исполняемый файл | Выяснить |
| Информационная база | Выяснить: файловый путь либо сервер и имя ИБ |
| Назначение базы | Всегда РАЗРАБОТКА (DEV), `database.environment=development`; не спрашивать |
| Авторизация базы | По умолчанию `infobase`: логин и источник пароля выяснить |
| Windows-аутентификация | По отдельному выбору способа авторизации базы; текущая учётная запись процесса агента, без вопроса о Windows-аккаунте |
| Основное хранилище | Выяснить наличие, использование, путь/адрес, свой логин и источник пароля |
| Источник актуальных исходников | Рабочая конфигурация Конфигуратора либо хранилище при подтверждённом наличии; выбрать отдельно для каждого компонента |
| Разрешения операций | По профилю; настройка не разрешает изменение бизнес-данных |

У каждого хранилища собственные реквизиты (`auth_kind=credentials`). Windows-аутентификацию
и логин базы в основное хранилище и хранилища расширений не наследуй.
Для каждого неизвестного источника пароля базы или хранилища задай один вопрос
«Каким способом передать пароль?» с явными вариантами «Локальный файл»,
«Переменная окружения», «Доступное хранилище секретов». Объясни варианты кратко:
пользователь сохраняет пароль в файле и сообщает путь; задаёт переменную, доступную
процессу 1С, и сообщает её имя; либо указывает запись фактически подключённого хранилища.
После выбора запроси только следующий неизвестный реквизит отдельным вопросом.
На «как передать пароль» отвечай этим же выбором; не проси сам пароль в чат.
Явное отсутствие пароля сохраняй как `password_ref.kind=none` без запроса источника.
Вместо паролей и токенов сохраняй ссылки на переменные окружения, файлы или выбранный
источник секретов. Значения не выводи в команды журнала, профиль, Git, отчёты и память.

AgentMemory используй только в явно разрешённой области согласно `memory` профиля.
При `memory.enabled=false` запрещены чтение, запись, автовыделение и вызов через мост;
не заменяй его другим сервисом памяти. Если память включена, перед существенной задачей
выполни поиск по известному объекту и действию и прочитай применимые записи через `memory_get`.
Изменчивые сведения перепроверь по файлам и системе. Глобальную область не подключай
без разрешения. Не сохраняй автоматически чувствительные адреса баз и хранилищ.
Память не является разрешением выполнять действия. При недоступности сообщи конкретный
ответ и продолжай независимую разрешённую работу.

При настройке и любом уточнении задавай строго один вопрос за раз об одном значении
или решении, затем дождись ответа. По возможности предложи варианты ответа.
Не объединяй несколько полей в одно предложение или форму. Сохраняй каждый ответ
сразу; известные значения повторно не спрашивай. Это правило сохраняется в
`questionnaire.questions_per_turn=1` и `questionnaire.prefer_choice_answers=true` профиля.

### Завершение развёртывания и очистка

После сохранения обязательных ответов, профиля, адаптированных рабочих правил и структуры
отметь `deployment.completed=true` и фактическое время `deployment.completed_at`.
Техническую готовность оцени отдельно: `status=blocked`, результаты проверок и причины
остаются достоверными. Не объявляй недоступные инструменты проверенными ради завершения.
Незавершённый опрос или отсутствие обязательных настроек не считаются завершённой установкой.

Агент обязательно сам очищает **целевую** `docs/развертывание/` перед итоговым сообщением;
в нормальном результате остаются только `ПРОФИЛЬ.json` и `СОСТОЯНИЕ.json`.
Распакованный источник сохраняется целиком. Очистка не затрагивает рабочие skills, остальные
docs, проверенные команды, секреты пользователя и имеющиеся компоненты или задачи.
Происхождение созданных или скопированных файлов и каталогов фиксируй в
`deployment.installation_artifacts`: `path` от корня проекта, `kind` (`file`/`directory`),
`origin` (`copied_from_template`/`created_by_deployment`) и `purpose`
(`installation_material`/`source_snapshot`/`permanent`). Совпадение имени не доказывает
происхождение; постоянные файлы не удаляй, исходники сохраняй по следующему порядку.

1. До изменений используй уже принадлежащий этому чату `docs/развертывание/НАСТРОЙКА.lock`
   либо захвати его эксклюзивным созданием нового файла с владельцем, временем и целью.
   Чужой lock останавливает изменения; свой повторно не захватывай и чужой не удаляй.
   Проверь фактические пути, их нахождение внутри целевого проекта и отсутствие
   переходов через reparse points. Используй точные пути
   и нативные операции одной оболочки; не удаляй всю папку или содержимое по маске.
2. Сохрани важные результаты, версии, ошибки и оставшиеся блокеры компактно в состоянии,
   без секретов. Ссылки на удаляемые журналы замени сохранённым результатом проверки.
3. XML/BSL и связанные ресурсы являются исходниками. Сразу размещай новые выгрузки в
   `1c_works_files`. Уже созданные в docs снимки сначала сохрани в
   `1c_works_files/components/main/src`, `1c_works_files/components/extensions/<имя>/src`
   либо отдельном каталоге снимка в `1c_works_files/tasks`, если рабочие
   исходники уже существуют. Не затирай имеющееся; проверь весь состав и хеши файлов
   новой копии до удаления исходной. Обнови пути профиля и состояния. Сохранённый снимок
   не заменяет свежий baseline перед разработкой.
   Удалять сохранённый оригинал в docs можно только при подтверждённом происхождении
   этой установки в `installation_artifacts`. Неизвестные пользовательские исходники
   сохраняй в docs даже после копирования, с `preserved_items` и блокером очистки.
4. По явному списку удали только подтверждённые материалы этой установки: `план.md`,
   `результат.md`, `проверки.md`, `ПРОФИЛЬ.example.json`, её диагностические журналы,
   файлы результата запуска, PID и записи команды. Неизвестные пользовательские файлы
   сохрани и перечисли в `deployment.cleanup.preserved_items`; не называй их мусором.
   Затем удали только подтверждённые собственные пустые диагностические подкаталоги:
   проверь полную пустоту, включая скрытые элементы; удаляй дочерние раньше родителей
   точными путями, без рекурсивного удаления. Сам `docs/развертывание` сохраняй.
   Неизвестные или непустые каталоги сохрани в `preserved_items` с причиной блокера.
5. Проверь ссылки README, рабочих правил, профиля и состояния. После успешного переноса
   исходников и удаления временных материалов удали `ИНСТРУКЦИЯ.md` последней из документов
   установки. Не оставляй действующих ссылок на неё в готовом проекте.
6. Установи `deployment.cleanup.status=done` и фактическое `completed_at` только после
   проверки итогового состава и ссылок. При ошибке или сохранённых неизвестных файлах
   укажи `blocked`, причину и следующий шаг; не скрывай проблему. Необходимую для
   продолжения инструкцию сохрани. Свой lock удали последним и затем проверь его отсутствие;
   ошибка освобождения блокировки означает `deployment.cleanup.status=blocked`.

Если очистка прервалась, продолжи только её по этим правилам и сохранённому состоянию.
Не запускай повторную установку, не сбрасывай ответы и не повторяй завершённые проверки.

## 1. Инструменты: skills и MCP

До каждого этапа определи и полностью прочитай подходящий skill выбранного набора.
Если профильный skill существует, выполняй операцию по нему. После изменения объекта,
формы, конфигурации, расширения, СКД, роли или макета выполняй соответствующую валидацию.
Не заменяй отсутствующий обязательный инструмент догадкой.

В начале разработки проверь необходимые для неё MCP реальными безопасными вызовами.
Сохранённый результат настройки не заменяет проверку текущей доступности инструмента.

Встроенные навыки с полным составом ресурсов:

- [Пакетный Конфигуратор 8.3.27](skills/1c-configurator-batch-8-3-27/SKILL.md).
- [Регистрация нового корневого объекта](skills/1c-add-new-object/SKILL.md).

Настройка выполняется напрямую по текстовой инструкции в распакованном шаблоне;
в целевом проекте её копия удаляется после завершения и очистки.
Служебный skill настройки не является частью рабочих навыков и в проект не копируется.

Весь комплект `skills/` сохраняй при подключении внешнего набора. Для другого выпуска
платформы выясни подходящий пакетный skill; сходство ключей не доказывает совместимость.
Вспомогательные скрипты запускай только для нужного действия, прочитав их инструкции.
`install.ps1` из batch-skill не является способом настройки всего проекта.

При развёртывании добавь таблицу выбранных внешних skills: операция, фактический путь
`SKILL.md`, версия, зависимости и область применения.

| Возможность MCP | Для чего использовать |
|---|---|
| Код и метаданные | Найти точный объект, код, структуру модуля, состав формы и вызовы до правки |
| Граф метаданных | Зависимости, область влияния, связи регистров, сравнение компонентов |
| Запросы в DEV | Проверка запросов и поведения, диагностика последней ошибки; изменяющий BSL только по прямому разрешению |

| Справка платформы | Проверить API платформы и встроенного языка |

| Шаблоны | Подобрать фрагмент и проверить его применимость к текущей конфигурации |

При настройке заполни реальные имена серверов, инструменты по их фактическим схемам,
связь с текущей базой/выгрузкой и результаты безопасных вызовов. Наличие порта, контейнера
или записи клиента не подтверждает работоспособность. Отсутствие инструмента в сессии
не доказывает отсутствие сервера: проверь настроенный транспорт. Проверяй JSON-RPC error
и `isError`. Не выдумывай метаданные. Недоступность обязательной возможности останавливает
её этап; независимые работы продолжаются. Старый индекс не считай свежим baseline.

## 2. Общие ограничения

Обычные изменения разработки разрешены только в РабочейПапке и для разрешённых компонентов.
ЯдроПроекта изменяй только при прямом запросе пользователя, включая настройку или исправление
эталона. Не клади в него XML-выгрузки базы, журналы задач, бинарные базы и секреты.
`skills/`, `docs/` и `docs/verified-1c-commands/` внутри ядра обязательны.

Запрещено:

- вводить новую переменную с именем `Параметры`;
- очищать `components` при любых обстоятельствах, удалять существующие выгрузки и чужие задачи;
- запускать `/CheckConfig` и `/CheckModules`, в том числе из примера или скрипта навыка;
- запускать Designer без `/DisableStartupDialogs`;
- запускать одновременно несколько пакетных процессов Designer;
- завершать чужие процессы `1cv8.exe`;
- изменять расширение или основную конфигурацию, запрещённые для редактирования;
- начинать разработку без свежего исходного состояния;
- продолжать зависимые этапы после обязательной ошибки;
- загружать частично подготовленное решение и помещать его в хранилище;
- автоматически повторять изменяющую операцию после неопределённого результата.

При ошибке останови зависимую цепочку, запиши команду без секретов и конкретную ошибку
в журнал задачи, сохрани подтверждённое состояние и сообщи блокер. До выяснения результата
не меняй следующие объекты, не загружай и не помещай изменения.

## 3. Создание задачи

Для каждой разработки создай отдельный каталог `РабочаяПапка/tasks/<ИдентификаторЗадачи>`.
По умолчанию идентификатор — `<НомерЗадачи>_<КраткоеОписание>`, без номера — `ai_<КраткоеОписание>`.
Описание отражает смысл, не длиннее 15 символов, без пробелов и символов `\ / : * ? " < > |`.
Другое правило применяется только по явно выбранной настройке пользователя.

Создай `DESIGNERlogs/`, `task.md`, `changed-files.txt`, `result.md`.
В `task.md` запиши требование, номер, выбранный компонент, причину выбора, этапы,
планируемые объекты и файлы. Не используй одну папку задачи для разных разработок.

Если полный список расширений ещё неизвестен, задай один вопрос «Как получить список
расширений?» с вариантами «Определить автоматически (рекомендуется)», «Указать вручную»,
«Расширений нет». Предлагай автоматическое определение, когда доступно подключение
и разрешено безопасное чтение текущей базы. Выбор сохраняй в
`extensions_discovery.method`: `automatic`, `manual` или `none`.
При `automatic` получи полный список точных имён через доступный инструмент по его
фактической схеме, проверив соответствие подключения базе профиля. Индекс другого
проекта и старые выгрузки не подтверждают текущий список. Не изменяй расширения, базу
и хранилища ради обнаружения. Сохрани доказательство чтения в состоянии настройки.
При ошибке сообщи конкретную причину и предложи ручной ввод отдельным вопросом;
не записывай ошибку как отсутствие расширений. Обнаруженные имена повторно не спрашивай.
При `manual` имена неизвестных расширений выясняй по одному. `extensions_confirmed=true`
означает успешное полное чтение либо подтверждённый пользователем полный список
или отсутствие расширений. Назначение, право редактирования, приоритет разработки
и реквизиты собственного хранилища уточняй отдельно по одному.

Строки расширений создаются только по ответу пользователя или подтверждённому чтению.
Отсутствие строк в эталоне не означает отсутствие расширений в новой базе.
Для расширений используй отдельные `components/extensions/<точное-имя>/src`.

Сначала оцени безопасную реализацию в разрешённом расширении. Оно должно позволять
выполнить требование полностью, соответствовать назначению и не требовать опасного
заимствования большого числа объектов или неоправданного дублирования типового кода.
Меньший числовой приоритет учитывай после этих условий; он не задаёт порядок применения
расширений в базе. Если расширение не подходит, выбирай основную конфигурацию, только
если её редактирование разрешено. Решение и причину запиши до изменений.

## 5. Пакетный режим Designer

Сначала найди подходящий рецепт в `docs/verified-1c-commands/`, проверенный в текущем
окружении и соответствующий платформе. Если его нет, используй пакетный skill.
Не придумывай параметры и не меняй сочетание ключей рецепта без технической необходимости.
Все команды выполняй в одной выбранной оболочке, правильно заключая пути в кавычки.

Для каждого вызова:

1. Создай отдельные файлы `/Out` и `/DumpResult`, если они поддерживаются командой,
   в `tasks/<ИдентификаторЗадачи>/DESIGNERlogs/`.
2. Имя журнала: `<НомерЭтапа>_<ДатаВремя>_<Операция>.log`.
3. До запуска запиши назначение, полную команду DESIGNER с замаскированными секретами,
   рабочий каталог и время. Добавь `/DisableStartupDialogs`.
4. Запусти один процесс и сохрани его PID. Ожидай завершения именно этого PID.
   Нулевая загрузка CPU не подтверждает завершение. Другие `1cv8.exe` не являются твоим запуском.
5. До завершения не начинай следующую пакетную команду и не меняй файлы её исходников.
6. Запиши код возврата, время, длительность, пути результатов, ошибки и предупреждения.
7. Проверь журналы, результат и фактический артефакт. Один код процесса не доказывает успех.

Если свой процесс долго существует без признаков завершения, не запускай второй и
не завершай его без явного разрешения. Запиши состояние в журнал, останови зависимую
цепочку и сообщи о возможном зависании. Не считай чужие `1cv8.exe` процессами агента.

## 6. Свежий baseline и контрольная XML-выгрузка

Для каждого компонента отдельно применяй выбранный `baseline_source`:

- `working_configuration` — свежая выгрузка рабочей конфигурации Конфигуратора;
- `repository` — актуальная версия из подтверждённого хранилища компонента: сначала
  разрешённое получение, затем свежая выгрузка рабочей конфигурации Конфигуратора.

Сначала выясни наличие хранилища одним вопросом. При `repository.exists=false`
источник — `working_configuration`; не предлагай отсутствующее хранилище.
При `exists=true` предложи два источника отдельным вопросом. Не выбирай хранилище
автоматически по одному адресу. Его использование, реквизиты и права должны быть подтверждены.
При `baseline_source=repository` обязательны `repository.exists=true`, `enabled=true`
и разрешённое получение (`permissions.get_configuration=true`). Отказ от захвата или
помещения не меняет источник и не отменяет использование хранилища для получения;
эти права (`capture_objects`, `commit_objects`) учитываются отдельно для требующих их этапов.
Для расширения речь идёт о его собственном хранилище, а не хранилище основной конфигурации.
При `repository` полное получение без `-Objects` необходимо до baseline. При
`working_configuration` не выполняй получение ради выгрузки; отдельно запрошенная
синхронизация допустима в своих границах, после неё baseline выгружается заново.
При отключённом хранилище не выполняй получение, захват и помещение.

Конфигурация БД не является вариантом `baseline_source`. Различай её состояние и
рабочую конфигурацию для загрузки, обновления и функциональных проверок. Не подменяй
выбранный источник конфигурацией БД и не заменяй рабочую конфигурацию ради проверки.
Выгружай компонент в его каталог; корректный прежний baseline обновляй по skill,
при его отсутствии сделай полную выгрузку без удаления имеющихся файлов.

После `MergeCfg`, загрузки XML или изменения рабочей конфигурации контрольная
`DumpConfigToFiles -update` выполняется **без `-getChanges`**. Проверь обновление
`Configuration.xml` и `ConfigDumpInfo.xml`, XML ожидаемого объекта и его регистрацию,
состав файлов и отсутствие посторонних изменений. Файл сравнения не доказывает обновление XML.

## 7. Основная конфигурация: этапы разработки

1. Проверь выбранный источник и права. При `baseline_source=repository` выполни полное
   разрешённое получение без `-Objects` по профильному skill из подтверждённого хранилища.
   При `working_configuration` начни с текущей рабочей конфигурации; получение ради baseline
   не требуется. Не перепривязывай хранилище для проверки подключения.
2. Определи, требуется ли синхронизация конфигурации БД до разработки. Если требуется,
   выполняй только разрешённое обновление; иначе зафиксируй отсутствие необходимости.
3. Выгрузи свежие XML в `components/main/src`, проверь результат и журналы.
4. До правки найди объекты и модули через MCP, проверь зависимости, составь точный план
   объектов и файлов в `task.md` и `changed-files.txt`.
5. При используемом хранилище захвати планируемые объекты до первого изменяющего шага.
   Проверь `repository.permissions.capture_objects`; запрет или неизвестное необходимое право
   блокирует этот шаг до отдельного уточнения, без обхода захвата.
   Не захватывай всю конфигурацию без необходимости. Чужой захват не обходи.
   Для нового объекта выполни предусмотренную инструментами последовательность владения;
   отсутствие документированного способа блокирует этот этап.
6. Для нового корневого объекта выполни раздел 8. Для существующего перейди к правке.
7. Измени только планируемые разрешённые файлы. Не меняй UUID, служебные свойства,
   окончания строк, кодировки и форматирование всего файла без необходимости.
   Обнови `changed-files.txt`, оставив только действительно изменённые файлы.
8. Проверь метаданные профильными skills, BSL — синтаксическим MCP, запросы — отдельно
   безопасным выполнением в актуальной базе. Соблюдай раздел 11.
9. Загрузи реально изменённые файлы документированным способом. Не подменяй обычную
   конфигурацию расширением. Частичность загрузки выбирай по возможностям платформы и skill.
   Список `-files` передавай отдельным аргументом по синтаксису skill. Для первичной
   регистрации нового объекта не добавляй `Configuration.xml` в частичную загрузку.
10. При необходимости и наличии разрешения обнови конфигурацию БД. Для нового каркаса
    сначала обязательна `verify-ready` по разделу 8.
11. Выполни контрольную выгрузку и проверку требования в DEV; проверь незапланированные
    изменения. Не проводи документы и не меняй бизнес-данные только ради проверки.
12. Только после успешной проверки при используемом хранилище помести нужные объекты
    с комментарием задачи и разрешением `repository.permissions.commit_objects`.
    При отключённом хранилище этот этап не выполняется.
13. Заполни `result.md` и проверь условия завершения из раздела 10.

В режиме `files_only` загрузка, обновление и проверка в DEV не выполняются. Это результат
работы с файлами; не объявляй его внедрённым изменением базы.

## 8. Регистрация нового корневого объекта

Раздел применяется только к новому корневому объекту основной конфигурации. Изменение
существующего объекта и добавление его формы, команды или макета не требуют этого сценария.
Используй [1c-add-new-object](skills/1c-add-new-object/SKILL.md) и все его зависимости.

Тип и имя возьми из требования и плана. До donor точечно проверь отсутствие полного
имени `<Тип>.<Имя>` в свежем `Configuration.xml`; не определяй его только по Git diff.
В папке задачи создай `new-object-merge/`; там размещаются manifest, неизменяемый снимок
baseline, donor XML, отдельная файловая ИБ, CF, настройки объединения и результаты проверки.
Не размещай эти артефакты в `components` или ядре.

Обязательная последовательность:

1. Подготовь manifest и сохрани неизменяемый снимок `Configuration.xml` с контрольной суммой.
2. Создай пустую donor-конфигурацию и минимальный каркас объекта. Для регистра накопления
   нужен технический donor-only документ-регистратор; в DEV его переносить нельзя.
3. Проверь donor через соответствующие `meta-validate` и `cf-validate` выбранного набора.
4. Создай отдельную файловую ИБ, загрузи donor XML без `UpdateDBCfg`, выгрузи `donor.cf`.
5. Настройки объединения: корень и вспомогательные объекты — `DoNotMerge`, только
   целевой объект — `GetFromSecondConfiguration`.
6. Выполни документированный `MergeCfg` без `-force`, `-ClearUnresolvedRefs` и
   `-IncludeObjectsByUnresolvedRefs`, учитывая права, поддержку и используемое хранилище.
7. До обновления БД сразу выгрузи рабочую конфигурацию. Подтверди добавление ровно
   целевого объекта, отсутствие удаления и посторонних объектов, наличие правильного XML.
8. Продолжи разработку по свежей выгрузке. Технические измерение и ресурс каркаса
   замени или удали; добавь реальный документ-регистратор для регистра накопления.
9. Перед `UpdateDBCfg` выполни `verify-ready`, затем предметную валидацию.

Если нужны обязательные ссылки, для которых нет проверенного donor-only сценария,
не создавай фиктивные зависимости и не очищай ссылки. Останови этап и выбери проверенный
сценарий на основе свежей конфигурации. Не пытайся регистрировать новый корневой объект
частичной загрузкой `Configuration.xml` и его файлов; `LoadConfigFromFiles` применяй
для последующей правки зарегистрированного объекта.

## 9. Расширения

Для каждого расширения проверь `editable`, точное имя, выбранный источник актуальных исходников,
исходники и хранилище. Расширения только для анализа не изменяй, не загружай и не обновляй.

Для разрешённого расширения без используемого хранилища:

1. Выгрузи именно выбранное расширение в его собственный каталог с точным `-Extension`
   по skill. Корректную прежнюю выгрузку обнови; при её отсутствии сделай полную.
   Не проверяй пустоту `components/main/src` для решения о выгрузке расширения.
2. По свежему baseline найди объекты и файлы, проверь заимствования, выполнимость
   требования и зависимости. До окончания анализа не изменяй файлы.
3. Разрабатывай только выбранное разрешённое расширение. Не меняй вместе с ним
   основную конфигурацию без технической необходимости. Если полная реализация
   в расширении невозможна, остановись, запиши причину и перестрой план; к основной
   конфигурации переходи только после её полного процесса актуализации.
4. Проверь изменение профильными skills и MCP. Загрузи только изменённые файлы,
   если это поддерживает skill, с точным именем расширения. Не загружай полную выгрузку,
   когда достаточна документированная частичная загрузка.
5. Разрешённым действием обнови расширение и конфигурацию БД, если это требуется.
6. Подтверди применение изменения и соответствие требованию, отсутствие изменений
   других расширений и основной конфигурации, отсутствие ошибок в журналах.
7. Заполни результат: имя расширения, объекты, файлы, загрузка, обновление и проверки.
   Получение, захват и помещение при отключённом хранилище не выполняются.

При используемом хранилище расширения: при `baseline_source=repository` сначала полное
получение без `-Objects`; при `working_configuration` получение ради baseline пропускается.
Затем свежая выгрузка рабочей конфигурации выбранного расширения, анализ, захват до правки,
разработка, валидация, загрузка, разрешённое обновление, проверка, помещение с комментарием задачи.
Используй собственные реквизиты и точный
`-Extension "<ИмяРасширения>"` по skill для каждой поддерживающей его команды.
Ограничения полной загрузки связанного с хранилищем расширения учитывай по документации;
не применяй непроверенный обход.

## 10. Условия успешного завершения

Задача завершена, когда создана отдельная папка, выбран разрешённый компонент, получен
свежий baseline, пройдены нужные именно этому сценарию этапы, изменены только запланированные
файлы, выполнены предметные проверки, сохранены журналы и заполнен `result.md`.
В `dev_full` отдельно подтверждаются загрузка и необходимое обновление DEV; при используемом
хранилище — захват и помещение, а получение — если требовалось выбранным источником
или отдельной синхронизацией. При отключённом — «не используется».
Не должно остаться необъяснённых изменений или ошибок обязательных этапов.

В результате укажи компонент, причину выбора, папку задачи, объекты и файлы, результаты
загрузки, обновления, помещения, проверки и ограничения. Не утверждай успех невыполненной
операции. Git, ветки и PR используй по выбранным правилам; перед коммитом проверь diff
и отсутствие секретов, баз и журналов.

Если пользователь выбрал Git и не изменил исходные правила, `main` содержит только
проверенное состояние; работа ведётся в отдельной `feature/<название>` или `fix/<номер>`.
Изменение оформляется PR, после проверки объединяется через Squash and merge;
завершённая рабочая ветка удаляется. Прямые изменения, force-push и удаление `main`
запрещены. Настройка не создаёт `.git` и remote до выбора пользователем.

## 11. Правила кода и проверки

Запрещено вводить новую переменную `Параметры`.
Псевдонимы источников запросов должны быть уникальны в каждом операторе `ВЫБРАТЬ`,
включая части `ОБЪЕДИНИТЬ`, и не совпадать с именами полей в области видимости.
В многотабличных запросах квалифицируй поля в `ВЫБРАТЬ`, соединениях, `ПО` и `ГДЕ`.
Назначай понятный псевдоним каждому источнику, включая табличные части.
Не угадывай состав полей: проверяй по метаданным. Синтаксическая проверка BSL не выявляет
все ошибки выполнения запросов; проверяй полный изменённый запрос в актуальной базе.
Для форм отдельно проверяй реквизиты, элементы, события и повторное заимствование.

По умолчанию пользовательские строки двуязычны: `НСтр("ru = '…'; en = '…'")`.
Другие языки возможны только по явно выбранному правилу проекта.
Каждое нетривиальное изменение сопровождай однострочным комментарием-маркером
в стиле конфигурации, с датой `YYYY.MM.DD` и, при наличии зарегистрированной задачи, её ключом:
`//<инициалы> <YYYY.MM.DD> <TASK-KEY> — <что изменено и зачем>`.
Инициалы и принятый стиль выясни в опросе, не подставляй чужие.

## 12. Проверенные команды

`docs/verified-1c-commands/` создаётся пустым при настройке и остаётся пустым до разработки.
Не клади туда README, `.gitkeep`, архивные примеры и проверки подключения при настройке.
Существующие рецепты текущего пользовательского проекта сохраняй.

Приоритет: подходящий проверенный рецепт текущего окружения, затем профильный пакетный skill.
В рецепте меняй только явно переменные параметры задачи: базу, расширение, пути, журнал,
список объектов; такие значения должны быть обозначены `<…>`.
Версию платформы и сочетания ключей перепроверяй при изменении окружения.
Если команда из skill успешно выполнена в ходе разработки и подтверждён результат,
сохрани или обнови рецепт с назначением, версией и признаками успеха без секретов.
Статическая корректность команды не делает её проверенной.
